

**Universal Rules for AI-Assisted Development (with PRD/Specs)**

---

## 1. 📌 Governing Principle

* The **Product Requirements Document (PRD)** or equivalent specification is the **single source of truth**.
* Before writing code, the coding agent must:

  1. Parse the PRD/spec carefully.
  2. Analyze the existing codebase.
  3. Generate a **customized steering/spec doc** (like Kiro’s Specs) that maps PRD → codebase.
* Code is written only after spec alignment.

---

## 2. 📌 Workflow (PRD → Spec → Code → Test → Ship)

1. **Read & Interpret Spec**

   * Extract roles, workflows, data models, APIs, state machines, and constraints.
   * Identify custom extensions (if mentioned).

2. **Analyze Codebase**

   * Check if modules/features are already implemented.
   * Document gaps, inconsistencies, and overlaps with PRD.

3. **Generate Steering Document (before coding)**

   * A structured doc including:

     * ✅ Module breakdown
     * ✅ State diagrams & workflows
     * ✅ Data model mappings
     * ✅ Required APIs/contracts
     * ✅ Testing strategy
   * This doc is tailored to the current codebase + PRD.

4. **Implement Incrementally**

   * Work module by module.
   * Respect existing interfaces & schemas.
   * Never regenerate the entire repo.

5. **Test & Verify**

   * Tests come from PRD requirements, not just the code.
   * Integration & RLS tests required.
   * CI/CD must be green before merge.

---

## 3. 📌 Contracts & Interfaces

* **DB schemas, APIs, and role permissions from PRD are immutable** once defined.
* All code must conform to them.
* If codebase already diverges, document deviation before touching.

---

## 4. 📌 Documentation First, Code Second

* Each feature starts with a **mini-spec** generated by the agent.
* Mini-spec includes:

  * Purpose
  * Input/Output contracts
  * Dependencies
  * Edge cases
  * Test plan
* Only after the mini-spec is approved → implement.

---

## 5. 📌 Testing Rules

* Tests are based on **PRD-defined acceptance criteria**.
* Once written, they must **not be altered by AI** to fit broken code.
* Always include:

  * Unit tests (validation, state transitions)
  * Integration tests (3rd party APIs, syncs)
  * E2E tests (role-based journeys)
* RLS (row-level security) must always be tested.

---

## 6. 📌 Prompting Rules for Coding Agents

When generating code, the agent must always:

* Reference the PRD/spec section + codebase location.
* Explicitly state:

  * “Do not modify unrelated files”
  * “Respect existing contracts/interfaces”
* Return **diffs/patches** where possible, not full rewrites.

---

## 7. 📌 Deliverables from Agent

For each task, the coding agent produces:

1. **Spec/Steering Doc** (PRD + codebase alignment)
2. **Proposed changes (diffs)**
3. **Tests** (unit/integration/e2e)
4. **Update to documentation**

---

## 8. 📌 Universal Guardrails

* ✅ If unclear, ask questions instead of guessing.
* ✅ Default to smallest safe change.
* ✅ Keep scope limited per request.
* ❌ Do not generate boilerplate for entire repo.
* ❌ Do not bypass tests or RLS/security rules.
* ❌ Do not silently change PRD contracts.

---

## 9. 📌 Applicable Contexts

This workflow applies to:

* New greenfield projects (start with PRD → generate steering spec → build incrementally).
* Existing codebases (map PRD → current state → identify gaps → extend safely).
* Any coding agent (Zencoder, Copilot, ChatGPT, Cursor, etc).
